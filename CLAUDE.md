# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Blazor Web App (.NET 9, render mode **Interactive Server**) that is the frontend for a
credit/loan management system ("CACE" — Sistema de Gestión de Crédito). It consumes a
REST API (`open_api.json`, tag-organized, `/api/v1/...`) and replicates a set of
Tailwind reference HTML mockups (`Dash.html`, `Creditos.html`, `ExpedientePersona.html`)
using Bootstrap 5 (vendored locally, no CDN) plus a custom `cace-*` CSS token system.

**Read `Src/CreditSystem.Frontend.Web/README/frontend-overview.md` before making any
non-trivial change.** It is the canonical, actively-maintained architecture doc — update
it whenever you add a screen, a service, or resolve one of the `DOCUMENTACION
INSUFICIENTE` items. What follows here is a condensed pointer to it, not a replacement.

## Commands

```bash
cd Src/CreditSystem.Frontend.Web

# restore Bootstrap (not fetched automatically on build)
dotnet tool install -g Microsoft.Web.LibraryManager.Cli   # once
libman restore

cd ../..
dotnet build
dotnet run --project Src/CreditSystem.Frontend.Web
```

There is no test project in this repo — verification is `dotnet build` plus manually
exercising the affected screen (see Dummy Data Mode below).

## Architecture: 3 strict layers

```
Components/Pages/*.razor   → only depends on I<Group>Service interfaces (DI-injected)
Services/Api/<Group>Service.cs → only depends on IApiClient; builds the route, maps Request→Response
Services/Api/ApiClient.cs (or Dummy/DummyApiClient.cs) → only place that serializes JSON,
    sets headers, and interprets HTTP error codes
```

Rules that must not be broken:

1. **Pages never inject `HttpClient` or `IApiClient` directly** — always an
   `I<Group>Service`. This is what makes Dummy Data Mode work without touching pages.
2. **One service per swagger tag** (e.g. tag "Loan Contracts" → `ILoanService`, "Cooperative
   Members" → `IMemberService`). Do not create a single mega-service.
3. **Every service method returns `ApiResult<T>` / `ApiResult`**, never throws for HTTP/network
   failures. Pages only branch on `IsSuccess` / `Data` / `Error` — no `try/catch` around HTTP.
4. **`Models/Requests`, `Models/Responses`, `Models/Enums` are a 1:1 mirror of the swagger**,
   marked `// <auto-generated>`. If the swagger changes, regenerate — don't hand-edit
   piecemeal. A few endpoints added by the backend after the last swagger sync are marked
   with a pointer to the backend source file instead (see frontend-overview.md §"Endpoints
   agregados").
5. **Every page follows the same internal shape**: `_isLoading` / `ApiError? _error` /
   `TData? _data` per data source, one `LoadXxxAsync()` per source, and conditional
   rendering `LoadingIndicator → ErrorState → content`. `Riesgo/Index.razor` is a short,
   representative example.

### Adding a new screen

1. Add `Request`/`Response` models under `Models/` if the endpoint doesn't have them yet
   (same shape as `open_api.json`, `<auto-generated>` header).
2. Add the method to the relevant `I<Group>Service` (or create the interface/impl pair for
   a new swagger tag), returning `ApiResult<T>`/`ApiResult`. The implementation only builds
   the `api/v1/...` route and delegates to `IApiClient`.
3. Register new services in `Program.cs`: `builder.Services.AddScoped<I<Group>Service, <Group>Service>();`.
4. Add `Components/Pages/<Module>/<Name>.razor` with `@page "/route"`, inject the service
   interface, compose with `PageHeader` + `DataTable`/`KpiCard`/`ConfirmDialog`.
5. Add the `NavLink` in `AppSidebar.razor`.
6. If something in the swagger is ambiguous (value catalog, format, unit), do not guess
   silently — leave a `DOCUMENTACION INSUFICIENTE` comment stating the assumption made.
7. Verify with `dotnet build` and by exercising the screen with `DummyData:Enabled = true`.

## Dummy Data Mode

`appsettings*.json` → `DummyData:Enabled` is a single switch (read in `Program.cs`) between
registering `IApiClient` as the real `ApiClient` or as `Services/Api/Dummy/DummyApiClient`,
which fabricates plausible response objects via reflection (`DummyDataFactory`) instead of
calling HTTP. No page or domain service is aware this mode exists. Useful for iterating on a
screen's layout before/without a live backend — but each call generates independent data (no
referential consistency across screens), so it's a layout tool, not a business-rule simulator.
When active, `AppHeader.razor` shows a "Modo Demo" badge.

## Known unresolved contract questions

Grep `DOCUMENTACION INSUFICIENTE` across the codebase for the full, current list (it is kept
accurate there, not duplicated here). The recurring themes: the swagger has no
`securityScheme` (ApiKey header name is assumed, configurable in `ApiSettings`), several enums
travel as raw integers with inferred (not confirmed) names, some `status` fields are free
strings with an inferred value catalog (`StatusBadge.razor`), and not all responses include
`currency` (`CurrencyFormatter.DefaultCurrency` = "NIO" is the presentation-only fallback).

## Configuration

`Api:BaseUrl` / `Api:ApiKey` / `Api:ApiKeyHeaderName` in `appsettings.json` — `BaseUrl` is
host-only (routes already carry `api/v1/...`). Never put a real `ApiKey` in
`appsettings*.json`; use `dotnet user-secrets set "Api:ApiKey" "..."` in development.
